# Waylist

> Progressive Web App для создания, планирования и совместного использования сложных автомобильных маршрутов.

## 1. Концепция

Waylist — это приложение для планирования поездок и автомобильных маршрутов.

Приложение не является навигатором и не должно пытаться заменить Яндекс Карты, Google Maps или другие картографические сервисы.

Основная задача Waylist:

- создать маршрут из последовательности точек;
- разбить маршрут на понятные сегменты;
- сохранить расстояние и предполагаемое время каждого сегмента;
- хранить ссылку на внешний картографический сервис для быстрой навигации;
- планировать остановки;
- добавлять заметки;
- делиться маршрутом;
- экспортировать маршрут;
- в будущем предоставлять рекомендации по остановкам и планированию.

Главный интерфейс должен быть ориентирован на **список/таймлайн маршрута**, а не на карту.

Карта является вспомогательным инструментом.

---

# 2. Формат приложения

Приложение должно быть:

- Progressive Web App (PWA);
- адаптивным;
- mobile-first;
- полностью работоспособным на мобильных устройствах и desktop;
- устанавливаемым на устройство через браузер;
- пригодным для использования в дороге;
- поддерживать offline-first подход для уже загруженных маршрутов.

Основной UX должен быть удобен на смартфоне.

---

# 3. Название

Рабочее название:

**Waylist**

Название должно быть вынесено в конфигурацию приложения, чтобы его можно было легко заменить без изменения архитектуры.

В UI название должно использоваться минимально:

- логотип;
- favicon;
- название приложения;
- metadata PWA.

Не использовать название в каждом экране.

```text
Trip
- id
- title
- description
- ownerId
- createdAt
- updatedAt
- startDate
- status
- visibility
- coverImage
```

Пример:

```text

12 сентября 2026

706 км
9 ч 20 мин
4 остановки
```

Point

- tripId
- title
- description
- address

- longitude
- type
- order
- arrivalTime
- departureTime
- duration
- notes
- externalLinks

# 4.3 Segment

Сегмент — один из главных объектов приложения.

Сегмент соединяет две точки.

```text
Segment
- id
- tripId
- fromPointId
- toPointId
- distance
- duration
- navigationUrl
- navigationProvider
- notes
- order
```

Пример:

```text
Москва
   ↓
178 км · 2 ч 20 мин
   ↓
Тверь
```

Для каждого сегмента пользователь может вручную указать:

- расстояние;
- время;
- ссылку на маршрут;
- картографический сервис;
- комментарий.

# 6. Создание маршрута

Пользователь нажимает:

**+ Новая поездка**

После этого:

1. вводит название;
2. добавляет стартовую точку;
3. добавляет конечную точку;
4. добавляет промежуточные точки;
5. меняет порядок точек;
6. создаёт сегменты между ними.

Добавление точек должно поддерживать:

- поиск по названию;
- ввод адреса;
- ручной ввод;
- координаты;
- создание точки из существующей точки;
- drag-and-drop изменение порядка.

# 9. Навигационные ссылки

Waylist не строит собственную автомобильную навигацию.

Пользователь может сохранить внешний navigation URL.

Минимально поддерживать:

```text
navigationUrl
navigationProvider
```

Поддерживаемые провайдеры на первом этапе:

- Yandex Maps;
- Google Maps;
- Apple Maps;
- Other.

UI:

```text
🗺 Яндекс Карты

[Открыть маршрут]
```

При нажатии приложение открывает ссылку во внешнем сервисе.

Важно:

**Waylist не должен самостоятельно модифицировать или пересчитывать внешний маршрут.**

Сохранённая ссылка считается источником навигации для конкретного сегмента.

# 10. Общая информация о поездке

В верхней части Trip отображать агрегированную информацию:

706 км

4 остановки

Автоматически рассчитывать:

- общее расстояние;
- суммарное время движения;
- суммарное время остановок;
- примерное полное время поездки;
- количество сегментов;
- количество точек.

# 11. Редактирование порядка

Пользователь должен иметь возможность менять порядок точек.

Использовать drag-and-drop.

Например:

```text
☰ Москва

☰ Тверь

☰ Валдай

☰ Санкт-Петербург
```

После изменения порядка:

- сегменты должны автоматически перестроиться;
- старые сегменты не должны теряться без подтверждения;
- приложение должно показать, что связанные navigation links могут требовать проверки.

# 13. Рекомендации

Рекомендационная система должна быть предусмотрена архитектурой, но не обязана быть сложной в первой версии.

В будущем приложение должно уметь рекомендовать:

- места для отдыха;
- АЗС;
- кафе;
- гостиницы;
- парковки;
- достопримечательности;
- оптимальное место остановки.

Рекомендации должны учитывать настройки пользователя.

Например:

```text
Предпочтения:

Остановка каждые: 2 часа
Максимальный участок: 200 км
Предпочитать: АЗС + кафе
Избегать: платные дороги
```

Будущая рекомендация:

```text
💡 Рекомендуем остановиться

Через ~25 км находится место,
которое соответствует вашим предпочтениям.

АЗС + кафе + туалет

[Добавить в маршрут]
```

На первом этапе достаточно подготовить интерфейс и data model.

# 14. Заметки

Заметки должны существовать на трёх уровнях:

### Trip notes

Общие заметки поездки.

### Point notes

Заметки конкретной точки.

### Segment notes

Заметки конкретного участка.

Пример:

```text
Сегмент Москва → Тверь

⚠️ Проверить состояние дороги
💬 Здесь обычно большая загрузка
```

# 15. Совместный доступ

Пользователь должен иметь возможность поделиться поездкой.

Основной сценарий:

```text
[Поделиться]
```

Создаётся share link:

```text
waylist.app/share/ABC123
```

Получатель может открыть маршрут без регистрации.

По умолчанию shared route доступен только для просмотра.

В будущем предусмотреть права:

```text
OWNER
EDITOR
VIEWER
```

# 16. Email-коммуникации

Приложение должно иметь возможность отправлять email.

Основные сценарии:

### Приглашение

```text
Евгений пригласил вас посмотреть маршрут:

Москва → Санкт-Петербург

[Открыть маршрут]
```

### Поделиться маршрутом

Пользователь вводит email:

```text
example@email.com

[Отправить]
```

Получатель получает:

- название поездки;
- краткую информацию;
- ссылку;
- имя отправителя.

Email-сервис должен быть абстрагирован от приложения.

Не привязывать бизнес-логику непосредственно к конкретному email provider.

# 17. Экспорт

Пользователь должен иметь возможность экспортировать маршрут.

Основной формат:

**JSON**

Пример:

```json
{
  "title": "Москва → Санкт-Петербург",
  "startDate": "2026-09-12",
  "points": [],
  "segments": []
}
```

Дополнительно предусмотреть:

- CSV;
- printable HTML/PDF;
- GPX в будущем.

Экспорт должен быть доступен из меню:

```text
⋮

Экспорт
├── JSON
├── CSV
└── PDF
```

# 18. Импорт

- переносить данные между пользователями.

# 19. Sharing + export

Важно различать:

### Share

Динамическая ссылка на поездку.

```text
waylist.app/share/ABC123
```

### Export

Файл со структурой маршрута.

```text
moscow-spb.json
```

Share предназначен для людей.

Export предназначен для данных.

# 24. Offline

PWA должна сохранять локальный cache.

В offline режиме пользователь должен иметь возможность:

- открыть ранее загруженные поездки;
- просматривать точки;
- просматривать сегменты;
- просматривать сохранённые navigation links;
- редактировать локальные данные.

После восстановления соединения изменения синхронизируются.

На первом этапе допускается простая стратегия:

```text
Server state
      ↕
Local cache
```

Полноценное conflict resolution можно реализовать позже.

# 27. UX principles

Главный принцип:

> **Route planning first. Map second.**

Пользователь должен понимать маршрут даже без открытия карты.

Приоритет:

1. точки;
2. сегменты;
3. остановки;
4. время;
5. расстояние;
6. заметки;
7. навигационные ссылки;
8. карта.

Не превращать приложение в копию Google Maps.

---

# 28. Mobile UX

На смартфоне:

- большие touch targets;
- минимум мелких элементов;
- sticky action bar;
- swipe gestures;
- drag-and-drop;
- быстрый доступ к навигации;
- минимальное количество экранов.

Особенно важно:

**Открытие навигации должно занимать максимум два нажатия.**

Сегмент

- регистрация;

- добавление точек;

# 34. Важное архитектурное решение

Не связывать сущность `Segment` с конкретным картографическим сервисом.

Использовать:

```text
navigationProvider
navigationUrl
```

а не:

```text
yandexUrl
```

Это позволит в будущем поддерживать:

```text
Yandex
Google
Apple
2GIS
Other
```

без изменения модели данных.

# 35. Важное UX-решение

**Пользователь должен иметь возможность создать полностью ручной маршрут.**

Не требовать от него использовать API карт.

Например:

```text
Москва
↓
Тверь

Distance: 178 km
Duration: 2h 20m

Navigation:
https://...

[Save]
```

То есть приложение должно быть полезным даже без интеграции с картами.

# 36. Главная ценность продукта

Waylist не отвечает на вопрос:

> "Как мне проехать из A в B?"

На этот вопрос уже отлично отвечают навигаторы.

Waylist отвечает на другой вопрос:

> **"Как мне организовать всю поездку из A в B с удобными остановками и понятными этапами?"**

Поэтому основной объект интерфейса:

**Trip → Points → Segments → Stops**

а не:

**Map → Route**

# 37. Definition of Done для MVP

Приложение считается готовым, если новый пользователь может:

1. зарегистрироваться;
2. создать поездку;
3. добавить старт и финиш;
4. добавить несколько промежуточных точек;
5. изменить их порядок;
6. увидеть сегменты между точками;
7. указать для сегмента расстояние;
8. указать время;
9. добавить ссылку на Яндекс Карты;
10. открыть навигацию;
11. добавить остановку;
12. добавить заметки;
13. увидеть общую дистанцию и время;
14. поделиться поездкой ссылкой;
15. отправить ссылку по email;
16. экспортировать поездку в JSON;
17. установить приложение как PWA;
18. открыть ранее загруженную поездку без сети.

Главное требование:

> **Приложение должно быть простым настолько, чтобы маршрут из 10–20 точек можно было собрать без ощущения, что пользователь проектирует авиаперелёт.**
